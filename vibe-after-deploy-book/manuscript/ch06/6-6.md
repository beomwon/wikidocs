# 6.6 트러블슈팅 — 에러 메시지별 원인

기상청 API는 에러 이름이 아주 친절한 편입니다. 영어 대문자가 길게 이어져 있어 처음엔 무섭게 보이지만, **이름만 읽어도 원인이 거의 특정됩니다.** 이 절의 표 하나면 6장에서 만날 문제의 대부분이 끝납니다.

에러는 두 군데에 나옵니다. `/api/weather`를 브라우저로 직접 열었을 때 화면에 보이거나, 터미널(로컬)이나 Vercel 런타임 로그(배포 후)에 찍힙니다. 어느 쪽이든 아래 이름 중 하나가 들어 있을 겁니다.

## 에러 이름별 대응표

| 에러 이름 (코드) | 이게 무슨 뜻인가 | 뭘 하면 되는가 |
|---|---|---|
| `SERVICE_KEY_IS_NOT_REGISTERED_ERROR` (30) | 등록되지 않은 키라는 뜻이지만, 실제로는 키가 틀린 게 아니라 인코딩 문제인 경우가 압도적이다 | 키를 다시 발급받지 말 것. 5.4절로 가서 Encoding 키와 Decoding 키를 서로 바꿔 넣어본다 |
| `SERVICE_ACCESS_DENIED_ERROR` (20) | 발급받은 키가 기상청 서버에 아직 동기화되지 않았다 | 아무것도 고치지 말고 기다린다. 5.6절 참고 |
| `NO_OPENAPI_SERVICE_ERROR` (12) | 요청한 주소나 오퍼레이션 이름이 존재하지 않는다 | 오퍼레이션 철자를 본다. `getVillageFcst`가 아니라 `getVilageFcst`다 |
| `APPLICATION_ERROR` (01) | `base_date` 또는 `base_time`이 잘못됐다. 아직 발표되지 않은 시각을 요청한 경우가 가장 흔하다 | 발표 시각 여덟 개 중 하나를 쓰고 있는지, 발표 직후 10~15분을 피했는지 확인한다 |
| `NODATA_ERROR` (03) | 요청한 격자에 데이터가 없다 | `nx`, `ny` 오타이거나 국내 범위를 벗어난 값이다. 6.2절에서 엑셀 값을 다시 확인한다 |
| `INVALID_REQUEST_PARAMETER_ERROR` (10) | 파라미터 값의 형식이 이상하다 | `base_time`에 `0230`처럼 정시가 아닌 값이 들어갔는지, 날짜 형식이 `YYYYMMDD`인지 본다 |
| `NO_MANDATORY_REQUEST_PARAMETERS_ERROR` (11) | 필수 파라미터가 빠졌다 | 6.1절 [조건]의 파라미터 여덟 개가 다 들어갔는지 Claude에게 확인시킨다 |
| `LIMITED_NUMBER_OF_SERVICE_REQUESTS_EXCEEDS_ERROR` (22) | 하루 요청 횟수를 넘겼다. 개발계정 기준 하루 10,000건이다 | 오늘은 기다린다. 그리고 7.3절의 캐싱을 반드시 붙인다 |
| `DEADLINE_HAS_EXPIRED_ERROR` (31) | 활용기간이 만료됐다 | 공공데이터포털 마이페이지에서 연장신청을 한다 |
| `DB_ERROR` (02), `HTTP_ERROR` (04), `SERVICETIME_OUT` (05) | 기상청 쪽 서버 문제다 | 내 잘못이 아니다. 고칠 게 없다. 잠시 뒤 다시 해본다 |

마지막 줄을 특히 기억해 두세요. **내가 아무리 코드를 고쳐도 안 되는 종류의 에러가 존재합니다.** 이걸 모르면 멀쩡한 코드를 밤새 뜯어고치게 됩니다. 이 세 개가 뜨면 손을 떼고 커피를 마시는 게 정답입니다. 그리고 이 경험이 바로 7장을 읽어야 하는 이유이기도 합니다.

## serviceKey의 대소문자 함정

하나 더 있습니다. 공공데이터포털 문서에는 파라미터 이름이 **`ServiceKey`**(대문자 S)로 적혀 있는데, 실제 호출에서는 **`serviceKey`**(소문자 s)를 쓰는 것이 통용됩니다.

문서를 성실하게 읽은 사람일수록 여기서 걸립니다. 문서대로 대문자로 썼는데 키를 못 알아본다는 에러가 나면, 키가 잘못됐다고 생각하게 되죠. 실제로는 이름을 못 찾아서 **키를 아예 안 보낸 것과 같은 상태**가 된 겁니다.

6.1절 프롬프트에는 소문자로 적어 뒀습니다. 그래도 에러가 안 풀리면 Claude에게 "`serviceKey` 파라미터 이름을 소문자 s로 보내고 있는지 확인해줘"라고 한 번 물어보세요.

## 표에 없는 에러가 떴다면

1권 3.6절에서 배운 방법 그대로입니다. **요약하지 말고 통째로 줍니다.**

> ```
> 날씨 API 호출에서 에러가 났어.
>
> 1. 하려던 것: 초대장에 모임 날 날씨 표시하기
> 2. 실제 결과: [화면에 뜬 것 또는 아무것도 안 뜸]
> 3. 에러 메시지 전문:
> [브라우저 화면 / 터미널 / Vercel 로그에서 복사한 전체]
>
> 기상청 단기예보 getVilageFcst를 서버에서 호출하는 구조야.
> ```

마지막 한 줄을 꼭 붙이세요. 어떤 API를 어떤 구조로 부르고 있는지 알려 주면 Claude가 엉뚱한 데를 뒤지지 않습니다.

에러 이름으로 바로 찾아보고 싶다면 **부록 C**에 이 책 전체의 에러 메시지가 한 곳에 모여 있습니다.

> **자주 막히는 지점**
>
> - *"로컬에서는 되는데 배포하면 날씨가 안 나와요."* — 대부분 Vercel 환경변수 문제입니다. `WEATHER_SERVICE_KEY`가 실제로 저장돼 있는지, 그리고 **값을 넣거나 고친 뒤 재배포를 했는지** 확인하세요. 환경변수는 재배포해야 반영됩니다(5.5절).
> - *"어제까지 잘 되던 날씨가 오늘 갑자기 안 돼요."* — 코드는 그대로인데 안 된다면 내 문제가 아닐 가능성이 높습니다. 표의 02·04·05번을 먼저 의심하세요. 그다음이 22번(한도 초과)입니다. 새로고침을 많이 눌러 본 날이라면 특히요.
> - *"날씨는 뜨는데 우리 동네 날씨가 아닌 것 같아요."* — 에러가 안 나면서 값만 이상한 건 격자 좌표가 틀린 경우입니다. `nx`와 `ny`를 서로 바꿔 넣었을 확률이 가장 높습니다. 6.2절 엑셀의 `격자 X`가 `nx`, `격자 Y`가 `ny`입니다.
> - *"비 오는 날인데 화면에 흐림이라고 떠요."* — 에러가 아니라 표시 규칙 문제입니다. `PTY` 우선 규칙이 코드에 반영되지 않은 것입니다(6.3절). Claude에게 "`PTY`가 0이 아니면 `SKY` 대신 `PTY`를 보고 표시해야 해"라고 그대로 말하세요.

프롬프트를 세 번 이상 다시 시켜도 AI가 제대로 못 만든다면, 붙들고 있지 말고 **부록 B**로 가세요. `/api/weather`가 어디서부터 어긋났는지 확인하는 법과, 그 한 조각만 다시 시키는 프롬프트가 순서대로 정리돼 있습니다. 거기까지 가는 일은 드물지만, 길이 하나 더 있다는 걸 알고 있는 것과 모르는 것은 다릅니다.

## 그런데 지금 잘 되는 건

날씨가 초대장에 떴다면 축하드립니다. 지도와 날씨가 나란히 붙었고, 초대장은 이제 꽤 그럴듯합니다.

다만 정확히 말하면, **지금 잘 되는 건 기상청이 오늘 잘 대답해 줬기 때문**입니다. 우리는 기상청이 4초 동안 아무 말이 없을 때 어떻게 할지, 하객이 몰려서 하루 10,000건을 넘겼을 때 어떻게 할지, 응답이 아예 안 올 때 초대장이 어떻게 보일지 — 아무것도 정해 두지 않았습니다. 6.1절에서 일부러 만들지 말라고 했으니까요.

다음 장에서 그 세 가지를 한 번에 두릅니다. **외부 API는 반드시 실패합니다.** 언제 실패하느냐만 남아 있습니다.

# 6.4 서버리스가 못 하는 일 — AI에게 시키면 안 되는 것들

서버리스 백엔드는 "요청 받고 → 빠르게 처리하고 → 응답하고 → 사라짐"에 최적화되어 있습니다. 뒤집으면, **오래 붙어 있어야 하는 일**은 못 합니다. 나중에 여러분이 AI에게 새 기능을 시킬 때 부딪힐 대표적인 벽들을 미리 알려드립니다.

## 못 하는 일 목록

**1. 실시간 연결 유지 (웹소켓)** — "실시간 채팅 넣어줘"라고 하면 AI는 웹소켓(연결을 계속 붙들고 있는 기술) 코드를 짜줄 수 있습니다. 로컬에선 됩니다. 하지만 Vercel 서버리스 함수는 잠깐 있다 사라지는 존재라, 연결을 계속 붙들 수 없습니다.

**2. 백그라운드 작업** — "메시지가 달리면 1시간 뒤에 알림 보내줘" 같은 요청. FastAPI에는 BackgroundTasks라는 "응답 먼저 보내고 뒷일은 천천히" 기능이 있는데, 서버리스에서는 응답을 보낸 백엔드가 곧 사라지므로 뒷일이 실행된다는 보장이 없습니다.

**3. 주기적 실행 (예약 작업)** — "매일 아침 9시에 참석자 집계해줘" 같은 것. 항상 켜져 있는 서버라면 알람을 걸면 되지만, 우리 백엔드는 그 시각에 존재하지도 않습니다. (Vercel에는 Cron Jobs라는 대체 기능이 따로 있습니다 — "정해진 시각에 깨워주는" 방식이라 서버리스와 어울립니다.)

**4. 긴 처리 (실행 시간제한)** — 서버리스 함수엔 실행 시간제한이 있습니다(무료 플랜 기준 수십 초 수준). "동영상 변환해줘" 같은 몇 분짜리 작업은 중간에 잘립니다.

**5. 파일 저장** — 6.2절에서 본 대로입니다. 업로드받은 사진을 서버에 저장? 사라집니다. 사진 저장은 전용 저장 서비스(오브젝트 스토리지)에 맡겨야 합니다.

## 이 목록을 어떻게 쓰나: 프롬프트에 한 줄 추가

외울 필요 없습니다. 새 기능을 시킬 때 이 한 줄만 붙이세요.

> **🗣️ 기능 추가 프롬프트에 상비약처럼 붙일 문장**
>
> ```
> 이 프로젝트는 Vercel 서버리스에 배포되어 있어.
> 서버리스에서 동작하지 않는 방식(웹소켓, 백그라운드 작업,
> 로컬 파일 저장 등)이면 코드를 짜기 전에 먼저 말해주고,
> 서버리스에서 되는 대안을 제안해줘.
> ```

이 한 줄이 있으면 AI가 "그건 서버리스에서 안 되니, 대신 이렇게 하시죠"라고 먼저 걸러줍니다. **환경을 알려주면 AI는 훨씬 똑똑해집니다.** 바이브코딩 전체를 관통하는 요령입니다.

## 그래도 꼭 필요해지면?

실시간 채팅이 꼭 필요한 서비스를 만들게 된다면, 그때는 항상 켜져 있는 서버 방식의 호스팅(Render, Railway, AWS 등)을 알아볼 때입니다. "더 알아보기"는 12장에서 짧게 안내합니다. 우리 초대장에는 필요 없습니다.

> **📦 이 장에서 배운 것**
>
> - 서버리스 = 요청 올 때만 실행됐다 사라지는 방식. 무료·자동 확장의 비결.
> - stateless: 기억이 유지 안 됨 → 메시지 증발 사건의 범인 → **저장은 외부 DB에** (7장에서 해결)
> - 콜드 스타트: 첫 접속 1~3초 지연은 정상
> - 오래 붙어 있는 작업(웹소켓, 백그라운드, 긴 처리, 파일 저장)은 못 함 → 프롬프트에 "서버리스야"라고 알려줄 것

이제 원인을 알았으니 고치러 갑시다. 다음 장에서 사라지지 않는 기억 — 데이터베이스를 붙입니다.

# 부록 D. 관리자 페이지 확장 — 개발자용 지름길

여기부터는 코드를 직접 만질 수 있는 독자를 위한 지면입니다. 본문에서 "이 책 범위 밖입니다"라고 넘긴 것들을 한자리에 모아, 방향과 함정만 압축해서 짚습니다. 코드를 길게 싣지는 않습니다. 무엇을 쓰면 되는지와 무엇을 조심해야 하는지가 이 부록의 값어치입니다.

## 이 부록의 쓰임

본문의 선택은 "더 나은 방법"이 아니라 "더 적게 배워도 되는 방법"이었습니다. 파이썬 문법을 모르는 독자가 혼자서 끝까지 갈 수 있는 경로를 우선했다는 뜻입니다. 그 선택들이 어디였는지 먼저 펼쳐 놓습니다. 아래 표에서 걷어내고 싶은 줄이 생겼을 때 해당 절을 보시면 됩니다.

| 본문의 선택 | 왜 그렇게 했나 | 확장하려면 |
|---|---|---|
| 관리자 인증은 HTTP Basic 하나 (10장) | 서버 상태 저장 없이 환경변수 하나로 끝난다 | D-1 |
| `/api/health`는 사람이 읽는 형태 (9.2절) | 관리자 화면 카드에 그대로 뿌리기 위해 | D-2 |
| 메모리 캐시 15분 (7.3절) | 저장소를 하나도 추가하지 않아도 된다 | D-3 |
| 타임아웃과 폴백만 (7.2절, 7.4절) | 재시도는 설명할 개념이 급격히 늘어난다 | D-4 |
| 에러는 관리자 화면에 모아 보기 (11.2절) | 외부 서비스 가입을 하나 더 시키지 않으려고 | D-5 |
| 알림은 하루 한 통 요약 메일 (11.4절) | 알림 피로가 기능 수명을 줄인다 | D-6 |
| 날씨는 단기예보만 (6장) | API 하나로 발급 절차를 한 번만 겪게 | D-7 |
| 지도는 JavaScript SDK만 (4장) | 브라우저 키 하나로 끝난다 | D-8 |
| 모임은 하나, 초대장도 하나 | 데이터 격리를 고민할 필요가 없다 | D-9 |

## D-1. 인증을 제대로 바꾸기

본문은 HTTP Basic 인증 하나로 `/admin`을 잠갔습니다. 관리자가 나 혼자일 때만 성립하는 구조입니다. 다음 넷 중 하나라도 필요해지면 갈아탈 때입니다. 관리자가 둘 이상, 권한 구분(보기 전용과 삭제 가능), 로그아웃, 그리고 누가 언제 들어왔는지의 접속 기록. 10.4절에서 "로그아웃 버튼을 만들지 말라"고 한 이유가 바로 Basic 인증에 서버 쪽 표식이 없기 때문인데, 그 표식을 만드는 것이 아래 방향들입니다.

**세션 쿠키 기반 로그인.** 사용자 테이블을 두고, 비밀번호는 해시로만 저장하고(bcrypt, argon2 계열), 로그인에 성공하면 세션 식별자를 담은 쿠키를 내려줍니다. 쿠키에는 `HttpOnly`, `Secure`, `SameSite`를 반드시 붙입니다. 로그아웃은 서버에서 세션을 지우는 것으로 끝나고, 접속 기록도 이때부터 남길 수 있습니다.

**여기서 서버리스의 함정을 만납니다.** 1권 6.2절에서 배운 stateless 성질 그대로입니다. 세션을 함수 메모리에 담아두면 다음 요청이 다른 인스턴스로 들어가는 순간 로그인이 풀립니다. 그래서 세션은 반드시 인스턴스 밖에 두어야 합니다. 선택지는 둘입니다. Neon에 세션 테이블을 만들거나, 서명된 토큰을 쿠키에 담아 서버가 아무것도 저장하지 않게 하거나. 후자는 저장소가 필요 없는 대신 즉시 무효화가 어렵습니다. 만료를 짧게 잡고 갱신하는 설계로 보완합니다.

**OAuth에 위임하기.** 관리자가 전부 구글 계정을 쓴다면 로그인을 통째로 넘기는 편이 낫습니다. 비밀번호를 보관하지 않아도 되고 2단계 인증도 남의 것을 빌려 씁니다. 대신 허용할 계정 목록(또는 도메인)을 우리 쪽에서 반드시 검증해야 합니다. "구글로 로그인했다"는 사실만으로 관리자가 되면 지구상의 모든 구글 계정이 관리자입니다.

**Vercel의 접근 보호 기능.** 배포된 사이트 앞단에서 접근을 막는 기능이 제공됩니다. 애플리케이션 코드를 건드리지 않고 배포 전체를 잠글 수 있다는 게 장점입니다. 다만 **어떤 보호 방식을 쓸 수 있는지는 플랜에 따라 다릅니다.** 여기서 단정하지 않겠습니다. 프로젝트 설정 화면에서 지금 내 플랜에 무엇이 있는지 직접 확인하세요.

**Basic 인증을 그대로 유지하기로 했다면**, 최소한 이 둘은 하세요.

- **비밀번호 비교를 타이밍 공격에 안전한 방식으로.** 문자열을 `==`로 비교하면 앞자리부터 몇 글자가 맞았는지가 응답 시간에 미세하게 드러납니다. 파이썬이라면 `secrets.compare_digest`를 씁니다. 아이디 비교도 마찬가지입니다.
- **HTTPS 강제.** Basic 인증은 아이디와 비밀번호를 요청 헤더에 거의 그대로 실어 보냅니다. 평문 HTTP로 한 번 열리는 순간 그대로 노출됩니다. HTTP 접속은 HTTPS로 돌려보내고, HSTS 헤더까지 붙이면 브라우저가 다음부터 알아서 HTTPS로만 접속합니다.

## D-2. 헬스체크를 표준에 맞추기

본문의 `/api/health`는 관리자 화면 카드에 뿌리기 좋은 형태로 만들었습니다. 사람이 읽는 용도죠. 여기에 감시 서비스나 로드밸런서 같은 **기계 독자**가 붙기 시작하면 다듬을 곳이 생깁니다.

**첫째, 상태 코드를 다르게 주세요.** 이게 가장 중요합니다. 감시 서비스 대부분은 본문 JSON을 파싱하지 않고 HTTP 상태 코드만 봅니다. 내부적으로 DB가 죽었는데 200을 돌려주면, 화면에는 빨강이 뜨는데 감시 서비스는 계속 "정상"이라고 말합니다. 정상이면 200, 비정상이면 503으로 나눠 주세요.

**둘째, 의존 대상별로 상태를 나눠 담으세요.** 전체 상태 하나와 함께 데이터베이스, 카카오맵, 기상청 각각의 상태와 소요 시간을 별도 항목으로 둡니다. 관리자 화면 여섯 칸이 이미 그 구조입니다. 이렇게 해두면 알림 문구도 "사이트 이상"이 아니라 "DB 연결 실패"로 구체화됩니다.

**셋째, 얕은 체크와 깊은 체크를 분리하세요.** 감시 서비스가 5분마다 헬스체크를 부르는데 그때마다 DB에 쿼리를 날리고 기상청까지 찌른다면, 아무도 안 들어오는 날에도 하루 288번씩 외부 API를 소모합니다. 기상청 단기예보 개발계정은 하루 10,000건이니 당장 터지진 않지만, 부르지 않아도 될 것을 부르는 구조인 건 분명합니다.

- **얕은 체크** — 프로세스가 응답하는지만 확인. 외부를 전혀 건드리지 않고 즉시 응답. 감시 서비스에 이 주소를 줍니다.
- **깊은 체크** — DB와 외부 API까지 확인. 관리자 화면이 열려 있을 때만, 또는 훨씬 긴 주기로 부릅니다.

**헬스체크 응답에 절대 담으면 안 되는 것.** 헬스체크는 인증 없이 열어두는 경우가 많아서 사실상 공개 문서입니다.

- 데이터베이스 접속 문자열 (호스트, 사용자명, 비밀번호가 통째로 들어 있습니다)
- API 키와 토큰 (마스킹한 앞 네 자리도 굳이 넣을 이유가 없습니다)
- 예외 스택 트레이스 (파일 경로와 라이브러리 버전이 함께 새어 나갑니다)
- 내부 호스트명, 사설 IP, 컨테이너 식별자
- 환경변수 목록

에러는 "database: error" 정도까지만 밖으로 내보내고, 원인 상세는 로그에만 남기세요.

## D-3. 캐싱을 제대로 하기

7.3절의 메모리 캐시 15분은 "저장소를 하나도 추가하지 않는" 대가로 정확성을 포기한 설계입니다. 서버리스에서는 함수 인스턴스마다 메모리가 따로 놀기 때문에, 동시에 세 인스턴스가 떠 있으면 캐시도 세 벌 생기고 기상청도 세 번 불립니다. 인스턴스가 회수되면 통째로 사라집니다. 캐시 적중률이 몇 퍼센트인지 예측할 수 없다는 게 본질적인 문제입니다.

대안은 셋입니다.

**DB 테이블에 캐시 저장.** 이미 있는 Neon을 쓰므로 새 서비스 가입이 없고, 모든 인스턴스가 같은 값을 봅니다. 9.4절에서 "마지막 성공 시각"을 띄운 것이 사실상 이 형태입니다. 대가는 캐시 조회마다 DB 왕복이 생긴다는 점 — 메모리보다 확실히 느리고, DB에 쓰기 부하가 조금 늘어납니다. 초대장 규모에서는 이 방법이 가장 무난합니다.

**외부 키-값 저장소.** 만료 시간 지정이 기본으로 있고 빠릅니다. 캐시를 위해 만들어진 물건이라 잘 맞습니다. 대가는 관리 대상이 하나 더 늘고 무료 범위를 넘기면 과금이 생긴다는 점. 조건은 서비스마다 다르니 가입 화면에서 확인하세요.

**HTTP 캐시 헤더로 CDN에 맡기기.** `/api/weather` 응답에 `Cache-Control`을 붙여 앞단 CDN이 대신 들고 있게 하는 방법입니다. 우리 함수가 아예 호출되지 않으므로 가장 저렴하고 빠릅니다. `s-maxage`로 CDN 보관 시간을, `stale-while-revalidate`로 만료 직후 갱신하는 동안 옛 값을 계속 내주게 할 수 있습니다. 대가는 캐시를 직접 비우기 어렵고 사용자별로 다른 응답에는 쓸 수 없다는 점입니다. 날씨처럼 모두에게 같은 값을 주는 응답에는 아주 잘 맞습니다.

**만료를 원본의 성질에 맞추기.** 고정 15분은 사실 근거가 약합니다. 기상청 단기예보는 `0200`, `0500`, `0800`, `1100`, `1400`, `1700`, `2000`, `2300` 여덟 번만 갱신되니, 발표 직후 받아온 값은 다음 발표까지 세 시간 동안 바뀌지 않습니다. 만료를 **다음 발표시각 + 여유 시간**으로 잡으면 15분 고정보다 호출은 훨씬 줄고 최신성은 오히려 좋아집니다. 여유 시간이 필요한 이유는 발표 직후에는 아직 데이터가 올라오지 않아 실패하기 때문입니다. 10~15분 정도 넉넉히 잡으세요.

## D-4. 외부 API 호출을 견고하게

**재시도와 백오프.** 모든 실패를 재시도하면 안 됩니다. 재시도해도 되는 것은 타임아웃, 5xx, 그리고 명백히 일시적인 것들뿐입니다. `NODATA_ERROR`(격자 좌표가 틀림)나 인증키 문제는 백 번 다시 불러도 같은 답이 옵니다. 간격은 지수적으로 늘리고(1초, 2초, 4초), 여기에 약간의 무작위값(지터)을 섞습니다. 지터가 없으면 여러 인스턴스가 동시에 실패했을 때 재시도 시점까지 나란히 맞춰져 원본 서버를 다시 때립니다.

**서버리스에서는 재시도가 오히려 위험합니다.** Vercel 함수에는 실행 시간 제한이 있습니다(정확한 값은 플랜과 설정에 따라 다르니 프로젝트 설정에서 확인하세요). 5초 타임아웃으로 세 번 재시도하면 최악의 경우 15초 이상을 쓰고, 실행 시간 제한에 먼저 걸려 **재시도 결과를 받아보지도 못한 채 요청 전체가 죽습니다.** 폴백을 돌려줄 기회조차 사라지는 거죠. 그래서 사용자 요청 경로에서는 재시도를 하더라도 한 번, 총 소요 시간에 상한을 두고 하세요. 재시도를 여유 있게 하고 싶다면 사용자 요청과 분리된 경로(예약 실행이나 백그라운드 갱신)로 옮기는 것이 맞습니다.

**서킷 브레이커.** 기상청이 30분째 죽어 있는데 방문자마다 5초씩 기다렸다 실패하는 것은 낭비입니다. 연속 실패가 임계치를 넘으면 회로를 열어 일정 시간 동안 아예 호출하지 않고 즉시 폴백을 내주고, 시간이 지나면 한 건만 흘려보내 살아났는지 확인합니다. 서버리스에서는 이 실패 카운터도 인스턴스 밖에 있어야 의미가 있습니다.

**동시 요청 합치기.** 캐시가 막 만료된 순간 100명이 동시에 들어오면 100개 요청이 전부 캐시 미스를 보고 동시에 원본을 부릅니다. 캐시를 붙였는데도 원본이 맞는 이 현상을 막으려면 같은 캐시 키에 대해 **한 번만 원본을 부르고 나머지는 그 결과를 기다리게** 합니다. 단일 프로세스라면 키별 잠금으로 되지만 서버리스에서는 인스턴스가 나뉘어 완전한 합치기가 어렵습니다. 현실적인 절충은 D-3의 `stale-while-revalidate` 방식입니다.

**타임아웃은 연결과 읽기로 나눠 잡으세요.** 하나로 뭉뚱그리면 둘 다 놓칩니다. 연결 타임아웃은 상대 서버에 손이 닿기까지 기다리는 시간이라 짧아도 됩니다(1~2초). 읽기 타임아웃은 상대가 답을 만들어 보내는 시간이라 조금 더 줍니다. 여기에 전체 요청의 상한도 따로 두세요. 연결 2초, 읽기 3초라도 리다이렉트를 몇 번 타면 합계는 훨씬 커집니다.

## D-5. 관측 가능성 — 로그를 쓸모 있게

11.2절에서 만든 것은 관리자 화면에 에러를 모아 보여주는 수준입니다. 혼자 운영하는 초대장에는 그걸로 충분하지만, 다음 단계는 이렇습니다.

**구조화 로그.** 한 줄에 하나의 JSON 객체로 찍습니다. 사람이 읽기엔 불편해도 검색과 집계가 되기 시작합니다. `"날씨 호출 실패: timeout"`이라는 문장 대신 `event`, `duration_ms`, `status`, `upstream` 같은 필드로 나누면 "지난주 기상청 호출 중 3초를 넘긴 비율"을 바로 뽑을 수 있습니다. 문장으로 남긴 로그로는 못 하는 일입니다.

**요청 식별자.** 요청이 들어올 때 임의의 식별자를 하나 만들어 그 요청에서 나오는 모든 로그에 붙입니다. 실패한 요청 하나가 어디를 거쳐 어떻게 죽었는지가 한 번의 검색으로 이어집니다. 응답 헤더에도 같이 내려주면 사용자가 "이 화면이 안 돼요"라고 캡처를 보냈을 때 그 식별자로 바로 찾아갈 수 있습니다.

**외부 에러 수집 서비스.** 에러를 DB에 직접 쌓는 방식은 DB가 죽으면 그 사실을 기록할 곳도 같이 죽는다는 약점이 있습니다. 에러 수집 서비스를 붙이면 예외가 자동으로 잡히고, 같은 에러는 묶이고, 발생 빈도와 스택이 함께 보관됩니다. Sentry 같은 것들이 대표적이고 대부분 개인 규모의 무료 범위를 둡니다. 조건은 가입 화면에서 확인하세요.

**지표를 시계열로.** 로그가 "무슨 일이 있었나"라면 지표는 "얼마나 자주, 얼마나 오래"입니다. 응답 시간, 에러율, 캐시 적중률, 외부 API 호출 수를 시간축에 남겨두면 "느려진 것 같다"를 "지난 화요일부터 p95가 두 배가 됐다"로 바꿔 말할 수 있습니다.

**개인정보는 로그에 남기지 않습니다.** 방명록 본문, 작성자 이름, 이메일, 전화번호, 접속 IP 전체, 인증 헤더, 쿠키 값 — 전부 금지 목록입니다. 로그는 백업되고 외부 서비스로 흘러가고 몇 달씩 보관됩니다. **DB보다 통제하기 어려운 저장소라고 생각하는 편이 안전합니다.** 꼭 필요하면 원본 대신 식별자나 해시를 남기세요.

## D-6. 알림 파이프라인

11.4절에서 넘긴 부분입니다.

**발신 도메인 인증이 첫 관문입니다.** 메일 발송 API를 붙일 때 가장 자주, 그리고 가장 조용히 걸리는 함정이 이겁니다. 코드는 정상이고 API는 200을 돌려주는데 메일이 안 옵니다. 스팸함에 들어갔거나 아예 폐기된 겁니다. 원인은 대개 발신 도메인 인증(SPF, DKIM 등 DNS 레코드 등록)을 하지 않은 것입니다. 서비스가 준 레코드를 도메인 DNS에 넣어야 하는데, 1권 9장에서 도메인 레코드를 만져봤다면 같은 화면입니다. **메일 기능을 붙일 때는 발송 코드보다 DNS 설정을 먼저 끝내세요.** 발신 주소를 아무 도메인으로나 적는 것도 같은 이유로 안 됩니다.

**중복 억제와 묶어 보내기.** 사이트가 죽으면 헬스체크 실패가 1분마다 쌓입니다. 그대로 알림을 걸면 메일함이 같은 내용으로 백 통 찹니다. 같은 종류의 알림에 키를 부여해 일정 시간 안에는 한 번만 보내고(중복 억제), 그 사이 발생한 것들은 세어 두었다가 "같은 에러 47건"처럼 한 통에 합칩니다(묶어 보내기). 그리고 상태가 회복됐을 때 **복구 알림을 반드시 보내세요.** 문제 알림만 오는 시스템은 "지금 괜찮은 건지"를 알 수 없어서 결국 안 믿게 됩니다.

**심각도 구분.** 최소 두 단계면 됩니다. 즉시 봐야 하는 것(사이트 다운, DB 접속 불가)과 나중에 봐도 되는 것(외부 API 간헐 실패, 응답 지연). 앞의 것만 즉시 발송하고 뒤의 것은 하루 요약에 넣습니다. 이 구분이 없으면 모든 알림이 같은 무게로 오고, 사람은 전부를 무시하는 쪽으로 적응합니다.

**카카오톡 알림톡이 개인 프로젝트에 과한 이유.** 사업자 등록이 필요하고, 발신 프로필을 만들어 심사를 받아야 하고, 보낼 문구도 미리 승인을 받아야 합니다. 기술적 난이도가 아니라 **행정 절차의 문턱**이 문제라는 뜻입니다. 코드 실력과 무관하게 개인은 출발선에 서기 어렵습니다. 세부 절차와 비용은 시점에 따라 달라지므로 여기서 옮겨 적지 않겠습니다. 사업자로 서비스를 운영하게 됐을 때 공식 문서를 확인하세요. 그전까지는 이메일이 모든 면에서 낫습니다.

## D-7. 날씨를 더 멀리 보기

단기예보로는 모임이 사흘 뒤를 넘어가면 답이 없습니다. 그다음은 **중기예보**입니다.

단기예보와 다른 점을 알아둬야 합니다. 첫째, 중기예보는 **별도의 서비스라서 따로 활용신청을 해야 합니다.** 단기예보 키가 있다고 그대로 쓸 수 없습니다. 공공데이터포털에서 "기상청_중기예보 조회서비스"(데이터 고유번호 15059468)를 찾아 5장과 같은 절차를 한 번 더 밟으세요. 둘째, **지역을 지정하는 방식이 다릅니다.** 단기예보의 격자 좌표(`nx`, `ny`)를 쓰지 않고 별도의 지역 코드 체계를 씁니다. 셋째, **응답 형식도 다릅니다.** 시간 단위 항목이 아니라 오전과 오후로 나뉜 일 단위 값에 가깝습니다.

여기서 더 구체적인 오퍼레이션 이름이나 파라미터는 적지 않겠습니다. 지어낸 값 하나가 몇 시간을 잡아먹으니, **해당 서비스의 상세 페이지와 활용가이드 문서에서 직접 확인하세요.** 5장에서 겪은 절차가 그대로 반복될 뿐입니다.

설계 방향은 분명합니다. **두 API를 하나의 창구 뒤에 숨기세요.** `/api/weather`가 날짜를 받아서, 사흘 이내면 단기예보를, 그 이후면 중기예보를 부르고, **화면에는 언제나 같은 모양의 응답을 내려줍니다.** 프론트엔드는 어느 쪽에서 온 값인지 몰라야 합니다. 다만 정확도가 다르다는 사실은 사용자에게 알려주는 편이 좋습니다. 열흘 뒤 예보에 기온을 소수점까지 찍어 보여주면 없는 신뢰를 만들어내는 셈입니다. "일주일 뒤 예보는 참고용입니다" 한 줄이면 충분합니다.

## D-8. 지도를 더 쓰기

4장에서 쓴 것은 지도를 화면에 그리는 JavaScript SDK뿐입니다. 카카오는 **로컬 REST API**도 제공하는데, 여기서 할 수 있는 일이 꽤 됩니다. 주소를 좌표로 바꾸기, 좌표를 주소로 바꾸기, 키워드로 장소 검색하기. 예를 들어 관리자 화면에서 모임 장소 주소를 입력하면 좌표가 자동으로 채워지는 기능은 이걸로 만듭니다.

**키가 다릅니다.** 이걸 놓치면 하루를 날립니다. 로컬 REST API는 이름 그대로 **서버에서 REST API 키로** 부르는 것이고, 지도에 쓰는 JavaScript 키와는 다른 키입니다. 반대도 마찬가지라 REST API 키를 지도 SDK에 넣으면 에러가 납니다. 그리고 REST API 키는 **절대 브라우저에 노출하면 안 됩니다.** 2.3절에서 나눈 "브라우저에 둬도 되는 키와 절대 안 되는 키" 구분이 여기 그대로 적용됩니다. JavaScript 키는 도메인 제한으로 보호되는 공개 키지만, REST API 키는 서버 환경변수에만 두세요.

**쿼터도 별도로 잡힙니다.** 지도 SDK와 로컬 REST API는 각각 세어집니다. 무료 쿼터는 개발자 계정에서 **첫 번째로 활성화한 앱에만** 제공되므로, 이 기능을 붙이겠다고 앱을 새로 만들면 안 됩니다. 기존 앱에 REST API 키를 그대로 쓰세요. 초과하면 429가 돌아옵니다.

**정적 지도.** 이미지 한 장으로 된 지도입니다. 카카오톡 미리보기 이미지, 메일 본문에 넣는 지도, 인쇄물처럼 자바스크립트가 실행되지 않는 자리에서 쓸모가 있습니다. 다만 **쿼터가 훨씬 작습니다.** 지도 SDK가 일 30만 건인 데 비해 정적 지도 조회는 일 1,000건 수준입니다(구체적인 수치는 공식 쿼터 안내에서 확인하세요). 미리보기 이미지처럼 방문자 수만큼 호출되는 자리에 무심코 쓰면 순식간에 바닥납니다. **정적 지도를 쓸 거면 반드시 결과 이미지를 저장해 두고 재사용하세요.** 모임 장소는 바뀌지 않으니 사실 평생 한 번만 부르면 됩니다.

## D-9. 여러 초대장을 한 화면에서

1권 10장에서 서브도메인 하나에 초대장 하나를 올리는 법을 배웠습니다. 모임이 늘어나면 프로젝트를 계속 복제할지, 한 프로젝트에 모임을 여러 개 둘지를 정해야 합니다. 세 개를 넘어가면 후자가 맞습니다. 배포도 한 번, 환경변수도 한 벌, 관리자 페이지도 하나면 됩니다.

**구조는 이렇습니다.** 모임 테이블을 하나 만들고, 모임마다 제목, 날짜, 장소 좌표, 격자 좌표, 공개 여부 같은 설정을 행 하나로 담습니다. 지금 코드와 환경변수에 흩어져 있는 값들이 전부 이 테이블로 옮겨가는 셈입니다. 방명록과 참석 응답 테이블에는 모임 식별자 컬럼을 추가합니다. 접근은 경로(`/e/모임식별자`)나 서브도메인으로 나누고, 서브도메인으로 간다면 와일드카드 DNS와 인증서, 카카오 도메인 등록을 함께 챙기세요. 도메인 등록은 최대 10개까지이므로 와일드카드로 넣는 편이 낫습니다.

관리자 화면은 **목록과 상세로 나눕니다.** 목록에는 모임별 상태와 방명록 수 정도만 보여주고, 상세에서 지금의 여섯 칸을 그대로 씁니다. 서버와 DB 카드는 모임과 무관하니 목록 화면 위쪽에 한 번만 두면 됩니다.

**여기서 데이터 격리를 실수하면 남의 모임 방명록이 보입니다.** 이게 이 절에서 가장 중요한 문장입니다. 조회 쿼리 어딘가에 모임 조건을 빠뜨리면 전체 방명록이 한 화면에 섞여 나옵니다. 개인 초대장에서는 청첩장 하객 명단이 다른 사람 돌잔치 페이지에 뜬다는 뜻이고, 이건 버그가 아니라 사고입니다. 대책은 셋입니다. 모임 식별자를 개별 쿼리에 손으로 넣지 말고 조회 계층 한 곳에서 강제할 것, 삭제와 수정 요청이 들어왔을 때 대상 레코드가 **정말 그 모임 소속인지** 반드시 확인할 것, 그리고 서로 다른 모임 두 개를 만들어 격리가 실제로 지켜지는지 테스트로 고정해 둘 것. 사람의 주의력에 맡기면 언젠가 반드시 뚫립니다.

## D-10. 이 책 범위를 넘어서는 신호

관리자 페이지를 계속 직접 만들 것인지, 기성 관리 도구를 붙일 것인지를 판단할 때가 옵니다. 아래 중 둘 이상이 해당하면 직접 만드는 쪽이 손해입니다.

- **관리자가 여럿이다.** 사용자 관리, 초대, 탈퇴 처리를 직접 만들기 시작하면 이제 본업이 그것이 됩니다.
- **권한을 나눠야 한다.** 역할과 권한 모델은 직접 만들면 항상 어딘가 구멍이 납니다.
- **감사 로그가 요구된다.** 누가 언제 무엇을 지웠는지를 남겨야 하는 상황은 대개 "요구받아서" 옵니다. 그 시점엔 이미 늦습니다.
- **데이터가 커졌다.** 방명록이 수만 건이 되면 목록 화면, 검색, 페이지네이션, 인덱스를 전부 손봐야 합니다.
- **관리 화면 고치는 시간이 서비스 고치는 시간보다 길어졌다.** 가장 정직한 신호입니다.

기성 도구는 목록, 검색, 필터, 권한, 감사 로그를 이미 갖고 있습니다. 우리가 만든 여섯 칸짜리 대시보드는 그때도 남겨두세요. 기성 도구가 잘하는 것은 데이터 관리이고, "무엇이 고장났는지"를 색으로 말해주는 화면은 여전히 우리 것이 더 낫습니다.

마지막으로 기술이 아닌 이야기 하나. **개인정보를 다루기 시작하면 이건 기술 문제가 아니라 책임 문제가 됩니다.** 방명록에 이름만 받다가 연락처를 받고, 참석 여부를 받다가 식사 제한 사항을 받고, 그러다 계좌번호나 주소를 받게 됩니다. 하나하나는 사소한 추가였는데 어느 순간 남의 개인정보를 보관하는 사람이 되어 있습니다.

그러니 늘리기 전에 정하세요. **무엇을 왜 수집하는지, 어디에 얼마나 보관하는지, 언제 어떻게 지우는지.** 이 셋을 정할 생각이 없다면 **애초에 모으지 마세요.** 모으지 않은 정보는 유출되지 않고, 보관 기간을 고민할 필요도 없고, 지울 일도 없습니다. 이 책의 초대장이 이름과 짧은 메시지만 받는 것도 그래서입니다. 기능을 하나 더 붙일 때마다 "이걸 안 받으면 정말 안 되나"를 먼저 물어보는 습관, 그게 운영자가 갖춰야 할 마지막 기술입니다.
